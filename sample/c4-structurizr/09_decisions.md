# 9 アーキテクチャ上の決定

構成を決めた主な判断を、1件ずつ記録する。各決定は、状況・検討した代替案・決定・結果の4つと、関連するASR（品質目標・シナリオ・制約）で書く。

| 番号 | 決定 | 関連 |
| --- | --- | --- |
| ADR-1 | APIは、1つのアプリケーションとして作る（モジュラーモノリス） | Q1・Q3、OC1・OC2・OC3 |
| ADR-2 | 決済は、3秒で打ち切り、再試行しない | Q1・Q2、S1・S2 |
| ADR-3 | 在庫は、条件付き更新で引き当てる | Q1、S1 |
| ADR-4 | カード番号の入力は、[[決済代行サービス]]の画面で行う | Q4、S4、TC2 |
| ADR-5 | 決済手段は、`PaymentGateway`の裏に隠す | Q3、S3、OC5 |
| ADR-6 | APIは、2台以上で動かし、停止したコンテナを自動で置き換える | Q2、S2、OC2・OC4・TC4 |

## ADR-1 APIは、1つのアプリケーションとして作る

**状況**: 開発者3人と[[運用担当]]1人の体制で（OC1）、6か月後にリリースする（OC3）。注文・在庫・決済は、1つの注文として整合している必要がある。

**検討した代替案**
- A: 注文・在庫・決済を、別々のサービスに分ける（マイクロサービス）。サービスごとに、配備・監視・データベースが要る。注文の確定は、複数のサービスにまたがる処理になり、途中で失敗したときの取消を、自前で作る必要がある。運用1人では、負担が大きい。
- B: 1つのアプリケーションとし、内部を、注文・在庫・決済の部品に分ける（モジュラーモノリス）。

**決定**: Bを採る。

**結果**
- 良い点: 配備と監視が1つで済む。[[在庫の引き当て]]と注文の保存を、1つのデータベーストランザクションで行える。月額費用が小さい（OC2）。
- 悪い点: 負荷が高いときは、API全体の台数を増やす（部品ごとには、増やせない）。部品の境界は、規約だけでは崩れるため、パッケージの依存を、テストで検査する。
- 見直す条件: 注文が、1分に100件を超え続けたとき、在庫の部品の分離を検討する。

**関連するASR**: Q1・Q3、OC1・OC2・OC3

## ADR-2 決済は、3秒で打ち切り、再試行しない

**状況**: 決済代行サービスの応答は、通常1秒以内だが、まれに10秒を超える。待ち続けると、[[利用者]]を待たせ（Q1）、データベースの接続も、占有する。契約中のプランは、同じ依頼の重複を防ぐ仕組み（[[冪等]]キー）に対応しない。

**検討した代替案**
- A: 応答があるまで、待つ。
- B: 3秒で打ち切り、自動で再試行する。決済代行サービス側で、すでに成功していた場合、二重に請求するおそれがある。
- C: 3秒で打ち切り、再試行しない。失敗として扱い、在庫を戻す。

**決定**: Cを採る。

**結果**
- 良い点: 応答時間の上限が決まる（S1。3秒に後処理を足して、3.5秒）。二重請求が起きない。
- 悪い点: 打ち切った後に、決済代行サービスでは成功している場合がある。注文は失敗として扱うため、利用者は、もう一度注文する必要がある。対策として、1日1回の夜間処理で、決済代行サービスの記録と[[照合]]し、食い違いを、翌朝、運用担当に通知する（OC4により、夜間に人は対応しない）。

**関連するASR**: Q1・Q2、S1・S2

## ADR-3 在庫は、条件付き更新で引き当てる

**状況**: [[セール期間]]は、同じ商品に注文が集中する（最大で30件/分）。

**検討した代替案**
- A: 行をロックして読み、更新する（悲観ロック）。ロックの待ちが、応答時間を伸ばす。
- B: 版番号で、衝突を検出する（楽観ロック）。人気商品では衝突が多く、再試行が増える。
- C: 条件付きの更新（`UPDATE stock SET qty = qty - :n WHERE item_id = :id AND qty >= :n`）を1回行い、更新された行の数で、成否を判定する。

**決定**: Cを採る。

**結果**
- 良い点: SQLが1回で済む。ロックを保持する時間が短い。在庫が、マイナスにならない。
- 悪い点: 複数の商品を含む注文は、商品ごとに更新する。デッドロックを避けるため、商品IDの昇順で更新する、という決まりを守る。

**関連するASR**: Q1、S1

## ADR-4 カード番号の入力は、決済代行サービスの画面で行う

**状況**: カード情報を自社で扱うと、PCI DSSの対象範囲が広がり、運用1人では守れない（TC2）。

**検討した代替案**
- A: 自社の画面でカード番号を入力させ、APIから決済代行サービスへ送る。
- B: 決済代行サービスが提供する入力画面（または、埋め込みの部品）で入力させる。自社には、決済用のトークンだけが届く。

**決定**: Bを採る。

**結果**
- 良い点: カード番号が、自社のAPI・データベース・ログに入らない（S4）。守る対象が、減る。
- 悪い点: 入力画面の見た目の自由度が、低い。決済代行サービスが止まると、注文できない（ADR-2により、3秒で失敗として扱う）。

**関連するASR**: Q4、S4、TC2

## ADR-5 決済手段は、`PaymentGateway`の裏に隠す

**状況**: 決済手段の追加の要望が、年に1〜2回ある。決済代行サービスの仕様変更は、3か月前に通知される（OC5）。

**検討した代替案**
- A: 決済代行サービスのSDKを、注文サービスから、直接呼ぶ。
- B: `PaymentGateway`というインターフェース（`charge`・`refund`・`listPayments`）を作り、決済代行サービスごとの実装を、その裏に置く。

**決定**: Bを採る。

**結果**
- 良い点: 手段の追加は、実装クラスの追加で済む（S3）。他の部品は、変えない。仕様変更への対応も、同じ実装クラスに閉じる。
- 悪い点: インターフェースは、手段に共通する操作（`charge`・`refund`・`listPayments`）だけを持つ。手段に固有の機能は、使えない。間接層が1つ増える。

**関連するASR**: Q3、S3、OC5

## ADR-6 APIは、2台以上で動かし、停止したコンテナを自動で置き換える

**状況**: 運用担当が1人で、夜間・休日に、人は対応しない（OC4）。1台の停止が、注文の停止になってはならない（Q2）。

**検討した代替案**
- A: 1台で動かし、停止したら、翌営業日に人が復旧する。
- B: 平常時は2台、セール期間は、最大6台。[[ヘルスチェック]]に失敗したコンテナを、自動で置き換える。
- C: 常に6台。

**決定**: Bを採る。

**結果**
- 良い点: 1台が止まっても、残りで注文を受け付ける（S2）。人の対応が要らない。Cより、平常時の費用が小さい（OC2。月額15万円以内）。
- 悪い点: 常に2台分の費用がかかる。APIは、利用者ごとの状態を、メモリに持たない（状態は、データベースに保存する）。

**関連するASR**: Q2、S2、OC2・OC4、TC4
