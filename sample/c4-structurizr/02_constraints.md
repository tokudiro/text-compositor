# 2 制約

この設計が従う制約を、3つに分けて示す。各制約には、設計への影響を書く。制約は、他の章から、IDで参照する。

## 2.1 技術的な制約

| ID | 制約 | 背景と、設計への影響 |
| --- | --- | --- |
| TC1 | 実装言語は、Java 21とSpring Bootにする | 開発者3人の全員が、Javaに習熟している。新しい言語を学ぶ時間は、取れない。→ 5章のAPIは、Spring Bootで構成する |
| TC2 | 決済は、契約済みの[[決済代行サービス]]を使う。カード番号は、自社のシステムに保存しない | 契約済みで、乗り換える予定がない。カード情報を保持すると、PCI DSSの対象範囲が広がり、運用1人では負えない。→ Q4。5章の決済クライアントは、カード番号を扱わない |
| TC3 | データベースは、PostgreSQLのマネージドサービスにする | [[運用担当]]が1人で、バックアップや更新を、自前で管理できない。→ Q2。7章の配置は、マネージドサービスに依存する |
| TC4 | 実行環境は、クラウドのコンテナ実行サービスにする。サーバーのOSは、自社で管理しない | OSの更新を、運用担当が行う余裕がない。→ 7章の配置は、コンテナ単位。Q2の自動回復に使う |
| TC5 | Webアプリは、直近2版のChrome・Safari・Edge（PCとスマートフォン）で動く | 閲覧の約7割が、スマートフォンから。古いブラウザへの対応は、費用に見合わない。→ 5章のWebアプリは、レスポンシブにする |

## 2.2 組織上の制約

| ID | 制約 | 背景と、設計への影響 |
| --- | --- | --- |
| OC1 | 体制は、開発者3人と運用担当1人 | 追加の採用予定がない。→ 構成を単純に保つ。Q3 |
| OC2 | クラウドの月額費用は、15万円を超えない | 事業の予算。[[セール期間]]の費用も、含めて守る。→ 7章は、負荷に応じて台数を増減し、平常時は最小にする |
| OC3 | 初回のリリースは、着手から6か月後。秋のセールの前に、間に合わせる | 売上の機会。→ 範囲を絞る（1.2の対象外）。新しい仕組みの採用は、最小限にする |
| OC4 | 夜間・休日の人による対応は、行わない | 運用担当が1人で、勤務時間は平日9〜18時。→ Q2。障害は、自動で回復する。7章に、監視と通知を置く |
| OC5 | 決済代行サービスの仕様変更は、3か月前に通知される | 契約上の取り決め。→ Q3。決済クライアントの差し替えを、3か月以内で完了できる構成にする |

## 2.3 規約

| ID | 規約 | 背景 |
| --- | --- | --- |
| C1 | 設計書は、arc42の12章の構成と、C4モデルの図で書く | 構成の標準があると、新しい開発者が、読む場所を探しやすい |
| C2 | コードの書式は、Google Java Styleに従い、Checkstyleで検査する | 3人の書き方を、そろえる。検査は、CIで自動化する |
| C3 | 文書とコメントは日本語、識別子（クラス名・API名など）は英語 | 開発者の母語は日本語。識別子は、慣習に従う |
| C4 | 外部向けのAPIは、REST・JSON・HTTPSで提供する。パスは、複数形の名詞にする（例: `/orders`） | Webアプリと、将来の他のクライアントが、同じAPIを使えるようにする。Q3 |
| C5 | 変更は、プルリクエストで行い、1人以上のレビューを必須とする | 3人の体制で、見落としを減らす |
