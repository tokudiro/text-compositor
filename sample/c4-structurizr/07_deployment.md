# 7 配置の見方

ECサイトを、クラウドのどこで、どう動かすかを示す。本番環境だけを書く。試験環境は、本番と同じ構成を、台数を最小にして作る（10章の試験は、この環境で行う）。

## 7.1 本番環境の配置

```structurizr
workspace {
    model {
        !include model.dsl
    }
    views {
        deployment ec production "Deployment" {
            include *
            autoLayout lr
        }
        styles {
            !include styles.dsl
        }
    }
}
```

## 7.2 台数と拡張の決まり

| 構成要素 | 平常時 | [[セール期間]] | 決まり |
| --- | --- | --- | --- |
| API（コンテナ） | 2台（各1 vCPU・2 GB） | 最大6台 | 2台以上を常に維持する（ADR-6）。平均のCPU使用率が60%を超えて3分続いたら、1台ずつ増やす。30%を下回って10分続いたら、1台ずつ減らす |
| Webアプリ | CDNから配信 | 同じ | 静的ファイルのため、台数の管理は要らない。キャッシュの有効期間は、1時間 |
| データベース | 主系1台と待機系1台（別のゾーン） | 同じ。接続数の上限だけ、セール前に引き上げる | 主系が止まったら、待機系に、自動で切り替わる（約1分） |
| ロードバランサ | マネージドサービス | 同じ | [[ヘルスチェック]]に失敗したコンテナを、振り分けの対象から外す |

- セール期間（年2回、各約1週間）の前に、事前の確認をする。6台まで増えても、データベースの接続数が足りることを、確かめる（S1）。
- データベースの接続数は、1台のAPIにつき20本とする。6台で、120本。データベースの上限（150本）に、収まる。

## 7.3 コンテナの停止と、自動置換

Q2・S2に対応する。6.3は「処理が途中で止まった注文」の回収だった。ここでは、コンテナそのものの回復を書く。

| 順序 | 出来事 | 時間 |
| --- | --- | --- |
| 1 | コンテナが1台、停止する | 0秒 |
| 2 | ロードバランサが、ヘルスチェックの失敗を検出する。10秒おきに確認し、3回続けて失敗したら、振り分けの対象から外す | 最長30秒 |
| 3 | 残りのコンテナが、リクエストを受ける。注文の取りこぼしは、起きない（2台以上を維持しているため） | 継続 |
| 4 | コンテナ実行サービスが、新しいコンテナを起動する | 約2分 |
| 5 | 起動したコンテナのヘルスチェックが通ったら、振り分けの対象に加える | 起動から約1分 |
| 6 | 6.3の「未確定の注文の回収」が、起動時に動く | 起動直後 |

停止から、台数が戻るまで、約3分半。10章のS2の目標（置き換えは5分以内）に収まる。

## 7.4 監視と通知

[[運用担当]]は1人で、夜間・休日に、人は対応しない（OC4）。そのため、自動で回復できないものだけを、通知する。

| 監視する項目 | 方法 | 通知する条件 | 通知先 |
| --- | --- | --- | --- |
| サイトの稼働 | 外形監視（1分おきに、トップページと、`GET /health`を確認） | 3回続けて失敗 | 運用担当へ、メールとスマートフォンの通知 |
| 注文の応答時間 | APIのログから集計 | 95パーセンタイルが、5分間、2秒を超える（S1） | 運用担当へ、メール |
| コンテナの台数 | コンテナ実行サービスの状態 | 2台を下回って、10分続く | 運用担当へ、メールとスマートフォンの通知 |
| データベースの空き容量 | データベースサービスの状態 | 使用率が80%を超える | 運用担当へ、メール |
| メールの送信失敗 | キューの再試行回数 | 3回失敗して、運用担当への通知に回った（5.8） | 運用担当へ、メール |
| 決済の食い違い | 夜間の[[照合]]（5.10） | 食い違いが1件以上 | 運用担当へ、翌朝のメール |

- 通知は、夜間に届いても、翌営業日に確認する。ただし、「サイトの稼働」と「コンテナの台数」の2つは、運用担当が、スマートフォンで確認できるよう、通知を分けている。
- 稼働率は、外形監視の記録から、毎月集計する（10章 S2）。

## 7.5 データの保護

| 項目 | 決まり |
| --- | --- |
| バックアップ | データベースは、毎日1回、自動で取得する。保持は7日。さらに、取得の時点まで戻せる機能（ポイントインタイムリカバリ）を、有効にする |
| 復元の確認 | 四半期に1回、バックアップから、試験環境へ復元して、注文の件数が合うことを確かめる |
| 暗号化 | 通信は、TLS 1.2以上。データベースとバックアップは、保存時に暗号化する |
| 秘密情報 | クラウドのシークレット管理に置く（8.4） |

## 7.6 リリースの手順

| 項目 | 決まり |
| --- | --- |
| 方式 | ローリング更新。コンテナを1台ずつ入れ替え、サイトを止めない |
| 手順 | 1. CIで、テストとCheckstyleが通ることを確認する（C2・C5）。2. 試験環境へ配備し、10章のS1・S4の検査を行う。3. 本番へ配備する。4. 外形監視で、5分間、異常がないことを確認する |
| 戻し | 異常が出たら、前の版に、コンテナを入れ替える。データベースの変更は、戻せるように、2段階（追加、のちに削除）で行う |
| 時間帯 | 平日の10時〜16時（運用担当が、すぐに対応できる時間）。セール期間の前後3日は、リリースしない |

## 7.7 月額費用の見積り

OC2（月額15万円以内）に対する、見積り。

| 項目 | 平常の月 | セール期間を含む月 |
| --- | --- | --- |
| コンテナ実行（API 2台、セール時は最大6台） | 4万円 | 7万円 |
| データベース（冗長構成） | 5万円 | 5万円 |
| CDN・ロードバランサ・外形監視・ログ | 1.5万円 | 1.5万円 |
| メール配信 | 0.5万円 | 1万円 |
| 合計 | 11万円 | 14.5万円 |

- セール期間を含む月でも、14.5万円で、上限（15万円）に収まる。ただし、余裕は0.5万円しかない。11章に、リスクとして書く。
- [[決済代行サービス]]の手数料は、売上に応じた費用で、この見積りに含めない。
