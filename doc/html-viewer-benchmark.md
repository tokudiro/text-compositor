# Viewer: HTML表示方法の計測（#180）

Viewer（[#165](https://github.com/tokudiro/text-compositor/issues/165)）が、HTML（[#161](https://github.com/tokudiro/text-compositor/issues/161)の出力）を、どのように表示するかを決めるため、候補を同じ条件で計測した結果である。計測用のコードと再現の手順は、[benchmarks/html-view/](../benchmarks/html-view/README.md)にある。

## 結論

- **決定: 既定の表示エンジンは、Electron（調整）とする**（2026-09-19）。実際に触った体感で、表示の遅れを、最も感じない（下記「体感」）。数値でも、何も描かれない白い時間が最も短く（約0.29秒）、画面が落ち着くまで0.52秒、メモリ約67 MB、プロセス3つである。代償は、Chromiumを同梱するため、配布物が大きいこと（展開後に約370 MB）である。この大きさは、Chromiumを同梱するツール（MarkText 396 MB、Ghostwriter 431 MB）と同じ規模で、許容する。削減は、行わない。
- **Tauri（wry）は、配布物が小さい**（実行ファイル0.5 MB＋OS標準のWebView2）うえ、メモリはElectronと同程度（約75 MB）である。しかし、**体感では、白い画面が出て、遅く感じる**。白い画面の対策（背景色・表示の遅延など）の効果が確認できるまで、推奨しない。
- **「ブラウザで表示」は、採用しない**（専用ウィンドウのアプリにする方針。参考値だけ測った）。**WebView2は、重くない。** ブラウザ引数で、標準の約124 MBから約80 MBに減らせる。
- 既存のMarkdown Viewer（Arto・Shiba・MDHero・MarkText・Ghostwriter）は、画面が落ち着くまでに、約0.6〜1.5秒かかった。1秒を超えると遅く感じる、という基準では、Arto（回によって0.6〜1.0秒）・MDHero（約1.0秒）・MarkText（1.3秒）・Ghostwriter（1.5秒）が、外れる。Shibaは、約0.9秒で、境界線上で、**白い画面が出ることが多い**（体感）。

エンジンの**切り替え**（より速いエンジンや、JavaScriptを使わない軽量なエンジンへの差し替え）は、別のissue（[#187](https://github.com/tokudiro/text-compositor/issues/187)）で扱う。

## 体感（利用者の確認）

利用者が、自作の最小アプリと既存のツールを、実際に起動して確認した（1人の所感。2026-09-19）。

| 候補 | 体感 |
| --- | --- |
| **Electron（調整）** | **表示の遅れを、最も感じない** |
| WebView2（.NET） | wryよりましだが、白い画面が出る |
| Tauri（wry） | 白い画面が出て、遅く感じる |
| Shiba | 白い画面が出ることが多い |

**体感の遅さは、「すべてが出るまでの時間」ではなく、「白い（何も描かれない）画面が見える時間」で決まる。** wryは、画面が落ち着くまでの数値では、WebView2より速い（0.70秒対0.83秒）のに、体感では遅い。計測では、「起動から画面が落ち着くまで」に加えて、「何も描かれない時間」（下記の「空白」）を、主な指標にする。

## 判断の基準

- **起動から表示まで1秒以内。** 1秒を超えると、遅く感じる（利用者の所感）。
- **何も描かれないウィンドウを、長く見せない。** Shibaは、約0.8秒の空白の後に、内容が現れる。
- **再読み込み（保存のたび）で、画面が乱れず、位置が動かない。** Shibaは、保存のたびに、編集位置へスクロールする。
- 軽さ（メモリ・プロセス数・配布サイズ）と、安定性。

## 計測の条件

- 環境: Windows 11、Intel Core i7-12700K、RAM 64 GB。WebView2ランタイム153.0、Electron 44.4.3、.NET 10、Rust 1.97、wry 0.57、tao 0.37。
- 全候補に、同じ固定のHTML（`fixture/index.html`。見出し・表・コード・alert・画像・図（Mermaid・svg）・`:::`のレイアウトブロックを含む。約12 KB）を表示させた。既存のツールには、同じ内容の標準GFMの原稿（`fixture-gfm.md`）を開かせた（拡張記法を除いた点だけが違う）。
- 自作の最小アプリは、HTMLを表示して、ファイルの変更を検知して再読み込みするだけである。JavaScriptは使わない（図は、生成済みのSVGを`<img>`で表示する）。
- 各候補を10回（画面の計測は8回）測り、初回を除いた平均を使う。初回は、プロファイルの作成などで遅い（WebView2は約2.4秒、Electronは約1.0〜1.5秒）。
- **メモリ**は、プロセスツリー全体の、プライベートなワーキングセットの合計（タスクマネージャーの「メモリ」に近い値）。
- **画面の計測**は、ウィンドウを、最前面の同じ位置・大きさ（1000×800）に置き、画面を繰り返しキャプチャして、変化を見た（`benchmarks/html-view/bench-visual.ps1`）。
- **「調整」**とは、ブラウザ引数`--disable-gpu --in-process-gpu`（GPUを無効にして、GPU処理をブラウザのプロセスに統合する）。

## 結果: 自作の最小アプリ

| 構成 | 起動（読み込み完了） | 画面が落ち着く | 再読み込み | プロセス数 | メモリ |
| --- | --- | --- | --- | --- | --- |
| ホストのみ（WinForms。基準） | 0.15秒 | - | - | 2 | 12 MB |
| WebView2（.NET）標準 | 0.65秒 | 0.84秒 | 22 ms | 8 | 124 MB |
| WebView2（.NET）調整 | 0.66秒 | 0.83秒 | 22 ms | 7 | 80 MB |
| **Tauri（wry）標準** | 0.51秒 | 0.71秒 | 40 ms | 8 | 119 MB |
| **Tauri（wry）調整** | **0.50秒** | **0.70秒** | 40 ms | 7 | **75 MB** |
| Electron 標準 | 0.42秒 | 0.52秒 | 32 ms | 4 | 116 MB |
| Electron GPU無効 | 0.43秒 | - | 33 ms | 4 | 75 MB |
| **Electron 調整** | **約0.45秒** | **0.52秒** | 33 ms | **3** | **67 MB** |
| （参考）WebView2 単一プロセス（非公式の`--single-process`） | 0.56秒 | - | 22 ms | 4 | 80 MB |

- 再読み込みは、どれも20〜40 ms。wryは、ファイルの更新日時を15 msごとに確かめる実装のため、その分が上乗せされている。
- 再読み込みの後は、メモリが、約20 MB増える。
- **WebView2の重さの大半は、GPU関連である。** 調整で、約35%減った（124 MB→80 MB）。起動時間は変わらない。ホストの分（約12 MB）を除くと、WebView2本体は、約70 MBが下限である。
- 単一プロセスは、メモリが調整と同じで、プロセスが減るだけである。Chromiumが正式にサポートしない指定のため、採用しない。
- **調整の副作用**として、GPUを使わない（ソフトウェア描画になる）。スクロールの滑らかさは、未確認である。

## 結果: 起動時の画面（何も描かれない時間）

ウィンドウが出てから、文書の内容が描かれるまでの時間（空白）を、画面のキャプチャで測った（8回の平均）。

| 候補 | ウィンドウ表示 | 内容が出る | 空白 | 画面が落ち着く |
| --- | --- | --- | --- | --- |
| Electron（自作、調整） | 0.18秒 | 0.46秒 | 0.29秒 | 0.52秒 |
| Tauri（wry）（自作、調整） | 0.17秒 | 0.35〜0.72秒（2つの山） | - | 0.70秒 |
| WebView2（.NET）（自作、調整） | 0.29秒 | 0.82秒 | 0.53秒 | 0.82秒 |
| Arto | 0.20秒 | 0.36秒 | 0.16秒 | 0.57秒（別の計測では1.03秒） |
| **Shiba** | 0.06秒 | 約0.87秒 | **約0.82秒** | 0.92秒 |
| MDHero（Tauri） | 0.05秒 | 0.2〜0.7秒 | 約0.3秒 | 約1.0秒 |
| MarkText（Electron） | 0.52秒 | 1.17秒 | 0.65秒 | 1.33秒 |
| Ghostwriter（Qt） | 0.90秒 | 1.15秒 | 0.25秒 | 1.47秒 |
| （参考）mo（ブラウザのタブ） | - | 0.25秒 | - | 0.49秒 |

- 既存のツールは、図（Mermaid）などを、**表示のときに描画**している。自作は、生成済みのSVGを表示するだけなので、その差が、約0.4〜0.5秒ある、と推測する（未確認）。
- **内容が描かれるまでウィンドウを表示しない**方式を試した。Electronでは、空白が0.29秒から0.16秒に減ったが、画面が落ち着くまでが0.52秒から0.71秒に延びた。wry・WebView2では、総時間が延びる、または、透明なウィンドウのため、空白が測れなかった。背景色をページに合わせる方式も、併用できる（未試験）。
- **測定の限界**: 内容の判定は、画面の中央部で、背景と違う画素が2%を超えたときとした。ばらつく回がある（Arto・MDHero・Shiba・wry）。傾向を見る目的で使い、絶対値としては扱わない。

## 結果: Viewer本体（#190）

Viewer本体（Electron、Pythonの常駐ワーカーでMarkdownをHTMLにして表示）を、同じ方法（画面のキャプチャ、8回の平均）で測った。Markdownは、`fixture/fixture.md`（図はキャッシュ済み）。

| 項目 | 結果 |
| --- | --- |
| ウィンドウ表示 | 0.18秒 |
| 内容が出る（＝画面が落ち着く） | **0.86秒**（0.82〜0.92秒） |
| ウィンドウが出てから、内容が出るまで | 約0.67秒（この間は、ツールバーと「変換中…」を表示する） |
| 再読み込み（`F5`。キャッシュ済み） | 約10 ms（ワーカーの応答。表示の更新を含む） |
| 再読み込みでのスクロール位置 | 保たれる（1200 pxにスクロールして再読み込みし、1200 pxのまま） |
| **自動更新**: 保存から表示の更新まで（本文の編集） | **約0.18秒**（0.18〜0.20秒。変化が止まるのを待つ150 msを含む） |
| **自動更新**: 図（Mermaid）を変更したとき | 1回目 約1.7秒（Mermaid用のブラウザの起動を含む）、2回目以降 **約0.20秒**（ブラウザを使い回す） |
| 自動更新でのちらつき（保存のたびの画面の乱れ） | なし（違う画面が0枚） |

- **自動更新の目標値**（[#170](https://github.com/tokudiro/text-compositor/issues/170)）: 保存から表示の更新まで**0.5秒以内**（本文の編集、参照する画像の変更、図の変更の2回目以降）。実測は、0.18〜0.20秒で、満たす。図を初めて描く1回目は、Mermaid用のブラウザの起動のため、約1.7秒かかる（目標の対象外）。目標は、1秒以内に表示する（起動）より厳しくした。保存のたびに待つ時間で、短いほうが、書きながら確認しやすいため。計測は、`viewer/scripts/check-auto-reload.js`（保存から、内容の見出しが変わるまでの時間。変化が止まるのを待つ150 msを含む）。
- **起動から表示まで1秒以内**を満たす（0.86秒）。自作の最小アプリ（Electron、約0.52秒）との差は、Pythonの常駐ワーカーの起動（約0.43秒）と、変換の分である。
- 起動時の白い画面は、ウィンドウとビューの背景色を、ページに合わせて（明・暗）、目立たなくしている。空白の時間は、最小アプリ（約0.29秒）より長いため、ツールバーと「変換中…」の表示で、待っていることを伝える。
- 図が未キャッシュの原稿（Mermaidのブラウザの起動を含む）の初回の変換は、約2〜3秒かかる（2回目以降は、キャッシュされ、速い）。

## 結果: 再読み込みのちらつき

ファイルの先頭行の末尾の空白を、足す・除くことで、内容を実際に変えて（見た目は同じ）、再読み込みの間の画面を、連続でキャプチャした。前の画面と違う画面が出れば、ちらつきとする。

| 候補 | 結果 |
| --- | --- |
| 自作（WebView2・wry・Electron）、Arto、MDHero、Shiba | ちらつきなし（違う画面が0枚） |
| MarkText | 約0.12秒、画面の約5%が乱れる（WYSIWYGエディタのため） |
| Shiba（編集位置が、文書の途中・末尾のとき） | **保存のたびに、編集位置へ約1秒かけてスクロールする**（Shibaの「最終編集位置への自動スクロール」機能）。再描画の乱れではないが、画面が動く |

Viewerでは、**再読み込みで、スクロール位置を保つ**ことを、設計の原則にする。

## 表示の忠実度

固定のHTMLの、表・コード・日本語・alert・画像・SVGの図・`:::`のレイアウトブロック（2カラム・複数列・右寄せ・大きな文字）は、Chromium系（WebView2・wry・Electron）で、崩れずに表示された。3つは、同じ描画エンジンである。Linux・macOSのwryは、WebKitGTK・WKWebViewを使うため、表示の差が出る可能性がある（未検証）。

## 未実施・今後の確認

- **JavaScriptなしの軽量HTMLエンジン**（litehtml・Blitz等）は、計測していない。Tauri・Electronが1秒以内に収まったこと、表・SVG・CSSの表示品質に不安があること、調査に時間がかかることから、優先度を下げた。エンジンを差し替えられる構成（[#187](https://github.com/tokudiro/text-compositor/issues/187)）ができたあとに、試す。
- Linux・macOSでの計測と表示の確認。
- GPUを無効にした（ソフトウェア描画の）ときの、スクロールの滑らかさと、大きな文書での表示。
- 常駐化（2回目以降の起動を即時にする）と、背景色を合わせる方式の効果。
- 配布物の作り方と、WebView2ランタイムが無い環境（Windows 10）への対応は、#168で扱う。

## 判断のまとめ

| 観点 | Tauri（wry） | Electron |
| --- | --- | --- |
| 画面が落ち着くまで | 0.70秒 | **0.52秒** |
| メモリ（調整） | 75 MB | **67 MB** |
| 配布サイズ | **約0.5 MB＋OSのWebView2** | 約370 MB（Chromium同梱） |
| ランタイムの更新 | OSが、WebView2を更新する | アプリ側で、Electronを更新して配布する |
| 体感（白い画面） | 白い画面が見える | **遅れを感じない** |
| 描画の一貫性 | Windowsは、WebView2。Linux・macOSは、OS標準のWebViewで、差が出る可能性がある | 全OSで、同じChromium |
| 実装 | Rust（`text-compositor`の中核はPython。常駐ワーカーと、標準入出力で連携する） | JavaScript（Node.js） |

数値では、どちらも1秒の基準を満たす。しかし、体感では、**Electron（調整）だけが、表示の遅れを感じない**。wryは、配布物が小さい（約370 MB対、実行ファイル0.5 MB。OS標準のWebView2を使うため、その分は含まない）代わりに、白い画面が見える。判断の優先順位（①安定性、②見た目、③性能とサイズ。#166）に従い、**体感を優先して、Electron（調整）を既定にする**。wryの白い画面の対策（背景色をページに合わせる、表示を遅らせる等）は、#187で、WebView2の殻を作るときに試して、体感を再確認する。
