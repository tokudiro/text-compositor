# 開発の進め方

このリポジトリで作業するときの決まりです。人も、AIも、同じ決まりに従います（[#643](https://github.com/tokudiro/text-compositor/issues/643)）。

## 1. 作業の前に、issueを作る

- 新しい作業（機能・調査・修正）は、**先にissueを作ってから**、取りかかる。作業中に気づいた論点を、その場で決め切れず、後続のissueへ散らさないため。判断の理由も、履歴に残る。
- 「構想だけ」のときは、実装せず、構想のissueにする。
- issueは**日本語**で書く。ゴール（完了条件）を本文に書く。
- 技術的に成立しないと分かった案や、方針に合わない案は、**理由を書いて、`not planned`でクローズ**する（例: Kroki・UMlet・WireViz・BPMN・Blitzの試作）。
- **需要が確認できない記法・機能は、クローズしない。** 開いたまま、優先度を下げる（マイルストーンを後ろにずらす、または外す）。下げた理由は、コメントに書く。需要は、時間とともに変わるため。
- 完了の判断（マージ・クローズ）の前に、確認を取る。

## 2. コミット・PR・コード

- コミットメッセージとPRは、**英語**で書く。
- コード内のコメントは、**日本語**で書く。「何をしているか」ではなく、設計意図・背景・トレードオフなど、非自明な理由を書く。
- READMEは、英語版（`README.md`）を既定にし、日本語版（`README-ja.md`）を分ける。相互にリンクを張る。
- PRが、issueの**一部だけ**を解決するときは、`Refs #N`と書く。全部を解決するときだけ、`Closes #N`と書く（`Closes`だと、マージで、issueが閉じてしまう）。
- docs・README・版上げ（`pyproject.toml`）だけのPRでは、CI（`.github/workflows/test.yml`）は、起動しない（無関係な変更で、CIを動かさない方針。#97）。「チェックが0件」は、異常ではない。ローカルで、`pytest`を実行して、代わりにする。

## 3. 依存とライセンス

依存を足すときの判断は、[仕様書](spec.md)2章に従う（商用でも無償・ローカルで完結・配布物に全部入り）。GPL・強いコピーレフトのもの・透かしが入るもの・重い実行環境を要るものは、入れない（READMEにも書いている）。

## 4. 公開リポジトリに書かないこと

次のものは、コード・文書・コミットメッセージ・issue・PR・コメントの、どこにも書かない。

- 個人情報、社外秘の情報、非公開のリポジトリの名前・パス・内容
- 開発者個人の環境の事情（使っているセキュリティソフトの名前と、その動作など）

書く前に確認する。書いてしまうと、履歴の書き換え（force push）という、高い費用の対応が要る。書き換えても、GitHub上には、古いコミットのSHAと、PR本文の編集履歴が残り得る。

配布物のコード署名の要否のような、一般的な課題は、個人の環境の出来事に触れずに、書いてよい。

## 5. 一時ファイル

作業用の一時ファイル（スクリーンショット・計測結果・作業用のスクリプト・コミットメッセージやPR本文の下書き）は、リポジトリ直下の`temp/`に置く（`.gitignore`済みで、コミットされない）。システムの一時フォルダ（`%TEMP%`など）には、置かない。パスが長く、場所が分かりにくいため。

## 6. 日本語の文章

issue・文書・Releaseの日本語の節は、次のように書く。

- 一文は、短く（40〜60文字が目安）。一文に、複数の主張を詰め込まない。
- 結論を先に書く。段落は、1つの主張だけを扱う。
- 接続助詞の「が」を、つなぎ言葉として使わない。逆接は、文を区切り、「しかし」などを使う。
- 事実と、推測を区別する。確認していないことは、「推測です」「未確認です」と書く。
- 固有名詞・技術用語（Markdown・Typst・GitHub Actionsなど）は、アルファベットのまま書く。設定のキー・関数名・ファイル名は、`バッククォート`で囲む。
