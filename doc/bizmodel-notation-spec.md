# bizmodel 記法仕様（記法1: モノ・カネの流れ）

状態: ドラフト（Issue #447）。実装前の仕様案であり、DSLの文法は変わりうる。

> 由来と謝辞: この記法は、板橋悟氏が考案し、体系化された手法「ピクト図解」（登録商標）に着想を得ています。「ビジネスとは交換である」という大原則と、わずか5つの表記ルールで、ビジネスモデルを誰もが描けるようにした設計に、深く敬意を表します。
> 本記法は、非公式の取り組みです。公式のツールではなく、原典の代わりにもなりません。手法そのものを学びたい方は、考案者の書籍『ビジネスモデルを見える化する ピクト図解』と、公式サイト（pictozukai.jp）を、ぜひご覧ください。
> 図と文章は、原典から写さず、自前で作っています。

## 1. 範囲

- 対応する範囲は、原典の表記ルールver1.0（5つのルール）のみ。
- 対象外（後回し）: 補足（吹き出し）、応用的な表記、ビジネスモデルキャンバス（別の記法として、別issueで扱う）。
- 原典の記号体系の完全な再現は、目標にしない。簡素な記法として、自前の図形で描く。
- 最初の実装は、**2者間の取引のみ**（複数の取引・まとめ・タイムライン・複数の顧客を含む）。3者以上（一列・プラットフォーム）は、段階3で実装する。

## 2. 大原則

1. ビジネスとは「交換」である。取引は、モノの流れとカネの流れを、必ず対にして描く。
2. 絵心を要らなくするため、抽象化したシンボル記号だけで描く。

## 3. 記号

| 区分 | 名前 | 形 | 意味 |
|---|---|---|---|
| エレメント | ヒト（法人） | 縦長の長方形（建物のイメージ）。取引の数に応じて、高さが伸びる | 企業・組織 |
| エレメント | ヒト（個人） | 人型 | 個人 |
| エレメント | モノ | 円 | 商品・サービス |
| エレメント | カネ | `¥` | 価格・売上 |
| コネクタ | 販売 | 右向きの矢印。先端を塗りつぶす | モノの流れ（売り手から買い手へ） |
| コネクタ | 支払 | 左向きの矢印。先端が開いた標準的な矢印（塗りつぶさない） | カネの流れ（買い手から売り手へ） |
| オプション | まとめ | 右向きの波括弧 | 1つのヒトに対する、2つ以上のモノ・カネの流れを、ひとまとめにする（同時の購買） |
| オプション | タイムライン | 下向きの矢印に`T` | 時間の経過。上が先、下が後 |

- ver1.0の記号は、7種類（エレメント3・コネクタ2・オプション2）。
- 販売と支払は、上下に並べた**2本1組**で使う（原典の名称は「関係性」）。2種類の矢印は、価値の流れと、お金の流れを、視覚的に区別するために使い分ける。
- カネの記号は、既定を`¥`とする。原典の英語の図では、`$`が使われている。最初の実装は`¥`に固定し、通貨の記号の切り替えは、段階3で足す（9章）。
- 描画は、黒の単色の線画とする。強調色は、規則ではない（推測）。最初の実装では、色を付けない（追加の対応で、利用者が指定できる機能を検討する）。

## 4. 規則

| 番号 | 規則 | 検査 |
|---|---|---|
| R1 | 取引は、モノ（販売）とカネ（支払）を、必ずセットで描く | モノだけ・カネだけの取引は、構文エラー |
| R2 | 売り手（誰が）を左、買い手（誰に）を右に置く。商品（何を）は、上の矢印の上、価格（いくらで）は、下の矢印の下に置く | 配置で保証する |
| R3 | 購買のタイミングが同じなら「まとめ」、時間差があるなら「タイムライン」を使う | ブロックの種類で区別する |
| R4 | ターゲット顧客が同一人物なら、ヒトの記号は1つ。別の人物なら、別の記号 | 同じ識別子は同じ記号、別の識別子は別の記号 |
| R5 | 無料は「0円」の取引として書く。取引がないときは、取引そのものを書かない | 金額の省略は、構文エラー |

## 5. DSL（たたき台）

```
title "サブスクリプション型"
company Provider "配信事業者"
person User "ユーザー"
Provider -> User : goods "視聴権" / money "月額500円"
```

### 5.1 文

| 文 | 書き方 | 備考 |
|---|---|---|
| 記法の種類 | `type flow` | 1行目に書く。省略すると`flow`（記法1）。将来、`type canvas`（記法2）を足す |
| タイトル | `title "…"` | 省略できる。1回だけ |
| 法人の宣言 | `company ID "表示名"` | 縦長の長方形。表示名は、長方形の中に書く |
| 個人の宣言 | `person ID "表示名"` | 人型。表示名は、人型の下に書く |
| 取引 | `売り手ID -> 買い手ID : goods "商品名" / money "金額"` | モノとカネは、必ず両方書く（R1・R5）。`goods`と`money`の順は、どちらでもよい |
| まとめ | `bundle { 取引 … }` | 同時に購買される取引（R3）。波括弧で描く |
| タイムライン | `timeline { 取引 … }` | 時間差のある取引（R3）。上から順に、時間が進む |
| コメント | `# …` | 行頭または行末 |

- 識別子は、英数字と`_`。表示名は、`"…"`で囲む（日本語を、そのまま書ける）。
- 金額は、文字列として扱い、書式を検査しない（`"0円"`・`"月額500円"`・`"？円"`など）。
- 分からない値は、`"？"`（金額なら`"？円"`）と書く。売り手・買い手が分からないときは、表示名を`？`にする。空欄（`""`）と省略は、書き忘れとして、エラーにする（E01・E02）。

### 5.2 取引の描き方

```
bundle {
  Maker -> Customer : goods "商品A" / money "100円"
  Maker -> Customer : goods "商品B" / money "200円"
}
```

```
timeline {
  Maker -> Customer : goods "本体" / money "12,000円"
  Maker -> Customer : goods "消耗品" / money "2,000円"
}
```

- `bundle`・`timeline`の中の取引は、すべて同じ売り手・同じ買い手とする（原典の例に合わせる）。
- `bundle`は、組を縦に等間隔で並べ、組の右側に波括弧を置き、買い手を1つ描く。
- `timeline`は、買い手を最初の組の高さに置き、買い手の下から、下向きの矢印（`T`つき）を伸ばす。

### 5.3 顧客セグメント（R4）

```
company Shop "店"
person X "顧客X"
person Y "顧客Y"
Shop -> X : goods "商品A" / money "100円"
Shop -> Y : goods "商品B" / money "200円"
```

- 別の識別子は、別のヒトの記号として描く（同じ売り手から、複数の買い手へ）。
- 同じ識別子への取引が複数あるときは、同じ記号に集約する。

## 6. 配置

汎用のグラフ配置は使わない。型ごとに、決まった場所に置く。

| 型 | 配置 |
|---|---|
| 2者対向 | 売り手を左、買い手を右。上の矢印がモノ（円は矢印の上）、下の矢印がカネ（`¥`は矢印の下、金額は`¥`の下） |
| 同じ2者の複数取引 | 組を縦に、等間隔で並べる |
| 同じ売り手と複数の買い手 | 売り手を左、買い手を右に縦に並べ、各買い手の高さに、組を置く |
| 一列（A → B → C）・プラットフォーム | **段階3で実装する。** 原典の公式の研修資料に、例がある。取引の向き（売り手→買い手）に沿って、列が左から右へ増える。企業の高さは、取引数で決まる。同じ企業が、左側で仕入れ（買い手）、右側で販売（売り手）の取引を持つ |
| 上のいずれにも当てはまらない図 | エラーにして、ずれた図を出さない |

## 7. エラー

| 番号 | 内容 | 例 |
|---|---|---|
| E01 | 取引に、`goods`または`money`の片方がない | `A -> B : goods "x"` |
| E02 | `money`の金額が空 | `money ""` |
| E03 | 未宣言の識別子を使っている | 宣言のない`C`への取引 |
| E04 | 売り手と買い手が、同じ識別子 | `A -> A : …` |
| E05 | `bundle`・`timeline`内の売り手・買い手が、そろっていない | 別の相手との取引が混じる |
| E06 | 構文エラー | 未知のキーワード、閉じていない`"`や`{`、日本語の識別子、`type`の位置・値の誤り |
| E07 | 識別子を、二重に宣言している | `person User "…"`を2回書く |
| E08 | 取引が1つもない | 宣言だけの図 |
| E09 | 最初の実装（2者間）で、扱えない図 | 売り手が複数、企業が売り手と買い手の両方、同じ買い手が`bundle`と別の組に現れる |

エラーには、行と桁を含める。

## 8. AST（JSONにできる形）

```json
{
  "type": "flow",
  "title": "サブスクリプション型",
  "actors": [
    {"id": "Provider", "kind": "company", "label": "配信事業者"},
    {"id": "User", "kind": "person", "label": "ユーザー"}
  ],
  "groups": [
    {
      "kind": "single",
      "trades": [
        {"seller": "Provider", "buyer": "User", "goods": "視聴権", "money": "月額500円"}
      ]
    }
  ]
}
```

- `groups[].kind`は、`single`・`bundle`・`timeline`。
- パーサの出力と、レイアウトの入力は、このASTにする。text-compositorの内部の型には、依存させない。

## 9. 決定と未決

### 決定済み（2026-10-14）

- 取引の書き方: モノとカネを、`/`で区切った1文に書く（`A -> B : goods "…" / money "…"`）。片方だけの文は、構文エラーにする。分からない値は、`"？"`を書く。
- 金額の検査: 書式を検査しない（文字列として扱う）。空欄・省略は、エラーにする。
- 3者以上（一列・プラットフォーム）: 最初の実装には含めない。2者間の実装の後、段階3で実装する。
- 記法の切り替え: フェンス名・拡張子・設定のキーは、`bizmodel`の1つ。種類は、本文の冒頭の`type`宣言で指定する（`type flow`。省略時は`flow`）。既存のMermaid・PlantUMLと同じく、1ツール＝1フェンス名の流儀に合わせる。
- 強調色: 最初の実装は、黒の単色のみ。公式の資料の色（緑がかった色、注目企業の塗りつぶし）は、規則ではなく強調の手段と見ている（推測）。利用者が要素ごとに強調を指定できる機能は、追加の対応として、後で扱う。

- カネの記号: 最初の実装は、`¥`に固定する。3者以上の対応（段階3）に合わせて、DSLの宣言で通貨の記号を指定できるようにする（例: `currency $`。省略時は`¥`）。

### 未決
